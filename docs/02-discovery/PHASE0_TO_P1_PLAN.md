# PHASE 0 → PHASE 1 TRANSITION PLAN

## Current Phase
Phase 0 — Discovery

## Immediate Objective
Resolve the highest-impact product questions before creating detailed subsystem specifications.

---

# Step 1 — Complete Discovery Worksheet

Use:
DISCOVERY_WORKSHEET.md

The eight answers do not need to define the entire game.

They only need to remove ambiguity that could change the fundamental product direction.

---

# Step 2 — Director Consolidation

After the worksheet is answered, Project Director should:

1. compare answers against current foundation sources;
2. identify contradictions;
3. convert approved conclusions into explicit decisions;
4. update PROJECT_STATE;
5. update DECISION_LOG;
6. revise Product Thesis if necessary;
7. determine whether Phase 0 exit criteria are satisfied.

Do not move forward merely because all questions have text answers.

The answers must form a coherent product direction.

---

# Step 3 — Phase 0 Exit Gate

Recommended exit criteria:

- player fantasy is clear;
- strategic center is clear;
- player authority is roughly bounded;
- role of competition is understood;
- simulation philosophy is chosen;
- long-term identity is understood;
- major risks are documented;
- first vertical-slice boundary is plausible;
- no critical contradiction remains.

---

# Step 4 — Open First Specialist

Recommended first specialist:

**01 — Product & Game Design**

Primary responsibilities:
- formalize player fantasy;
- formalize design pillars;
- define product boundaries;
- define the management experience;
- identify core player decisions;
- draft the initial core loop;
- define what the game deliberately does NOT simulate.

Do not open Technical Architecture yet.

---

# Step 5 — Return to Director

The Product specialist should return a structured handoff.

Project Director then decides whether to:

A. request clarification / revision;

B. proceed to Core Loop & Simulation;

C. open targeted research;

D. resolve a product conflict.

# Important Boundary

Do not use Codex for production implementation yet.

Codex becomes valuable after the project has:
- explicit specifications,
- clear module ownership,
- acceptance criteria,
- and a validated minimal gameplay model.

This project documentation phase should produce the inputs Codex will later execute.
