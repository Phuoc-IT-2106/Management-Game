# Data-Driven Content Foundation

Status: PROPOSED. Date: 2026-10-04. Owner: Technical Lead with domain designers.

**DECISION:** DEC-020/021 do not make prototype coefficients, fictional discipline, counts or horizon production canon. No new gameplay systems are authorized by listing a content category.

**PROPOSAL:** Start with versioned JSON files and one schema per bounded category, loaded into immutable typed definitions. Keep authoring files readable and source-controlled. CSV/spreadsheet import can be a later adapter if needed; imported output must pass the same validation. Engine scenes/resources are appropriate for presentation assets, not authoritative gameplay definitions. No universal future-game schema or generic executable rule language is proposed.

## Category contracts

**PROPOSAL:** Fields below are minimal schema responsibilities, not finalized ratings or balance. Unsupported fields/mechanics are rejected or left out until approved.

| Category | Static definition content | Runtime campaign facts kept separately | Required validation |
| --- | --- | --- | --- |
| Players | Definition ID, display/localization key, discipline/role references, supported initial attributes and trait references | Entity ID, current attributes, readiness, availability, employer and development facts | Valid roles/traits and numeric ranges; unique IDs; no inactive prototype rating added without purpose |
| Staff | Role, supported capabilities, tendency profile, trait references | Employment, capability changes, authority assignments and knowledge | Initially Head Coach only; no implied deep staff hierarchy |
| Organizations | Identity/name/presentation references, initialization profile | Player company or compressed rival current state, commitments and history | One player-controlled company; no requirement for mirrored rival finances |
| Competitions | Discipline/rule references, eligibility and bounded calendar-generation configuration | Generated schedule, entrants, results and rulings | Unique fixtures, legal dates/participants and valid references; no fixed production match count |
| Sponsors | Identity, fit categories and permitted offer-template references | Available offers in World; signed terms in Company Contracts; delivery progress in Commercial | Valid categories, windows, referenced template IDs and permitted clause types |
| Contracts | Separate employment, sponsorship and financing template schemas; permitted clauses, schedule rules and units | Immutable accepted terms, counterparties, effective dates and Finance item IDs | Clause combinations, date order, monetary units, schedule totals and financing constraints |
| Traits | ID, applicable entity category and reference to an approved bounded effect kind | Assigned traits and any approved mutable duration/state | No arbitrary scripts; only implemented effect types; incompatibilities and cycles rejected |
| Balance/config | Domain-specific, named parameters with units, scale, bounds and rationale | No silent changes to a running campaign's rules | Range/cross-field constraints, explicit defaults and rule version; no unexplained copied prototype coefficients |

Use `category:namespace:slug` Definition IDs restricted to lowercase ASCII letters, digits, colon, underscore and hyphen, with a proposed 128-character maximum. IDs are never localized or reused for different meanings. Renaming an ID requires an explicit migration mapping; changing a display name does not. Runtime Entity IDs are different identifiers generated by the deterministic campaign allocator.

## Packs, manifests and validation

**PROPOSAL:** A pack manifest lists pack ID/version, category schema versions, required pack versions, sorted file inventory and SHA-256 hashes. Compute a manifest digest from a canonical inventory. Presentation-only files use a separate manifest so texture/font changes do not alter gameplay identity. Default initial scope is one built-in gameplay pack. A future pack system must reject duplicate definition IDs and ambiguous override order; executable mod loading is outside scope.

The validator runs without an engine and performs:

1. Syntax/schema checks, required fields, unknown-field rejection and file/record size limits.
2. Cross-file reference checks, unique IDs, units and numeric bounds; no hidden conversion of floats to money.
3. Domain rules: supported roles, contract schedules, meaningful configuration combinations, competition calendar feasibility and permitted effects.
4. Manifest integrity and deterministic ordering checks, including shuffled input files and culture-independent parsing.

Diagnostics contain file, definition ID, field path, violated rule and suggested correction. Errors block pack publication/campaign creation. Warnings need named ownership and may not mask broken references. Test fixtures include valid minimal packs and intentionally malformed packs. Schema validation alone cannot prove balance or strategic value.

## Runtime contract and editing

**PROPOSAL:** Load and validate a manifest once per session, then expose immutable definitions to domain resolvers. Staff/UI receive only observation-safe projections; access to the full catalog must not leak hidden person attributes. Static public rules may be shown without exposing private runtime state.

Development content edits create a new content identity. Apply them to a fresh campaign or an explicitly supported migration; never mutate definitions under a running deterministic session. Saves pin their manifest as specified in [persistence](PERSISTENCE_SAVE_LOAD.md). Balance changes require changed golden expectations plus design rationale, not silent test threshold relaxation.

**OPEN QUESTION:** Production discipline, world scale, data limits and numerical ranges need approved scope (Q-05/Q-08). Synthetic stress datasets exercise technical limits only. Data tooling is specified in [repository/tooling](REPOSITORY_BUILD_TOOLING.md); no content pipeline or production data has been implemented.
